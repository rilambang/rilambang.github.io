The iOS stack I actually reach for

3 min read · Muhammad Ilham Rilambang

Nobody hands you a blank project. You get a five-year-old codebase, a team, and one question that decides everything else: who's on call when this breaks at 3am? This is the stack I reach for then.

Language and concurrency

Swift, on the newest language mode the team can hold, with strict concurrency on rather than aspirational. Adopting it late costs more than adopting it early, because the cost is proportional to how much code you already have. Everything is main-actor by default and explicitly off it only where work is genuinely expensive — the opposite default produces code that's concurrent by accident.

UI

SwiftUI for new screens, UIKit where the platform still requires it or where a table or collection needs control the declarative layer doesn't yet give. That is an honest position rather than a religious one: a rewrite that ships is better than a purity that doesn't.

Navigation has one owner. Always. Two systems that both think they own the stack produce the worst bugs to diagnose.

Structure

Local Swift packages per seam, the app target as a thin shell. The reason isn't elegance — it's that an unchanged module doesn't get rebuilt, and a circular dependency becomes a compile error rather than a convention nobody follows.

Networking

Whatever the codebase already has, unless it's actively harmful. A second networking layer is a worse outcome than an imperfect first one. On a greenfield app I would reach for the platform's own concurrency tools over a reactive framework; on an existing app I leave the existing one alone until there is a reason to move it.

Persistence

The platform's own persistence before a hand-rolled SQL layer, and a real constraint in the schema before validation in the app. Constraints are enforced under concurrency and app bugs aren't. Where the data matters, the second copy of the truth is the one that goes stale.

Strings

A single string catalogue, referenced by key. Never a literal in a view — not because of localisation, though that too, but because a literal in a view is unsearchable and permanent. This is the cheapest discipline on the list and the one most often skipped.

Testing

Tests for logic, first and always: parsers, state machines, anything with a branch. They run in seconds and they catch the regressions that matter. UI tests sparingly, on the flows that carry money or data, because they're slow and inherently flaky and a flaky suite gets ignored — which is worse than not having one.

A test that can't fail isn't a test. If I can't describe the change that would turn it red, it's decoration.

Third-party dependencies

Only for a problem the platform doesn't solve. The bar isn't popularity. Can I read this library when it misbehaves, and is anyone still maintaining it in two years? A small dependency I understand beats a large one I don't, and "we might need it later" has never once been true.

Build health

Build warnings treated as a budget rather than as weather. A codebase with three hundred warnings can't notice the fourth hundred, and one of those was going to tell you that a main thread write had just become an act of faith.

The meta-decision

I've changed stacks more than once, and each time the framework-specific knowledge expired faster than I expected. What survived is the habit underneath it: prefer the boring choice, prefer the platform's own tool, prefer the option a new hire can debug on their first weekend on call, and leave the codebase so that the next person's hard problem is the interesting one — not the one you set up for them by being clever.

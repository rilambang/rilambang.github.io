What a green build does not prove

4 min read · Muhammad Ilham Rilambang

A green pipeline says the build succeeded. It says nothing about what went into it. This week five things I'd called verified turned out not to be, and every one failed the same way: I'd taken a colour as evidence about inputs.

The build that compiled a working copy

The pipeline went green and I reported what I believed it proved: CI read the committed dependency list, fetched each dependency at the revision the list named, and compiled against it. It proved the build succeeded. The input was wrong.

The runner was a shell executor whose build directory sits inside a developer's home directory — one level below the folder holding the dependency checkouts. So the code the build compiled wasn't fetched from the list at all. It was the local copies already on that disk, in whatever state the last person left them. No commit was required for an uncommitted edit to reach a build. The dirty-tree guard in the sync script existed and was correct; nothing on the publishing path called it.

The lesson isn't "configure your runner properly", though that too. It is that a pipeline's inputs are a claim, and the only way to hold that claim is to print them. A build that doesn't name its inputs in its own log is a build nobody can reproduce — including the person who pressed the button.

The lock file that pins a branch

The dependency list had one row per package and every row named a branch. Zero rows named a revision. That file looks like a lock and behaves like a wish: on one afternoon the branch on a single dependency moved twice, so the same app commit resolved to two different sets of code on two runs, and neither build's log said which one it got.

This is a cheap bug to have and a cheap bug to fix, which is why it's worth writing down. The script already supported a revision in that column — it falls back to a plain checkout when the name isn't a remote branch. So the fix is one column, and the cost is honest: bumping a pinned dependency becomes an explicit commit, and you can't fast-forward a pinned checkout any more. That is the trade you're buying. It is the whole point of the file.

The push that deploys twice

I said pushing the branch would deploy once. It deployed twice: once from the push, and again from the merge into the default branch. What I had actually verified was that the merge-request pipeline doesn't deploy — the rules exclude every source that isn't a push, in as many words — and I had quietly stopped counting there. Two, and the second one arrives after the review, when nobody is watching for it.

- if: '$CI_PIPELINE_SOURCE != "push"'
  when: never

The rule is a good design: a branch that hasn't been merged should not ship. But "the MR can't deploy" and "this work deploys once" are different sentences, and only the second one tells a tester how many builds are coming.

The release that changed nothing

Two builds went out carrying the same version and the same build number, both identical in content to a build testers already had. The version strings had been lost in a merge — three files quietly disagreeing about what the app was called — and restoring them was the right fix. It also meant an entire release whose only real change was a string.

Nothing in the store tells a tester that. The two releases are distinguishable only by an internal release id, which is exactly the kind of identifier nobody outside the console ever sees. The only artifact that can say "you have already tested this, there is nothing here" is the release note. So the note is hand-written, per release, and it's the one piece of writing in the process I won't generate: a changelog derived from commits would have said "fix version strings", which is accurate and useless.

The analytics change that was almost free

Identity handling moved from a per-event parameter to a first-class user property, and three custom parameters were dropped along the way. I called that free. A colleague checked the documentation instead of agreeing: one of the three is collected automatically with every event, and the other two aren't.

So the precise statement is narrower than "nothing was lost". The information survives, because the platform's own Platform and Operating system dimensions collect it. What dies is the custom dimension names — any report built on those literal parameter names goes blank on the next release. That is a five-minute console check, not a code change, and it's the sort of removal that stays unused right up until a chart proves otherwise.

What I do differently now

  • Print the revisions. Every job dumps the resolved revision of every dependency next to the app commit. If the inputs aren't in the log, the claim about the binary isn't evidence.
  • Pin revisions, not branches. In anything whose output ships. A branch in a lock file records intent; a revision records a build.
  • Count deploys from the rules file. Not from memory, and not from "the MR can't ship". Read what each pipeline shape does and add them up.
  • Put the purpose in the release note. Two identical builds and a tester who can't tell them apart is a documentation defect, not a testing plan.
  • Check "unused" against the documentation. Before deleting a field, find out whether something was already collecting it. "We never used that" and "the SDK always did" look identical in a diff.

The habit underneath all five is the cheapest one available: verify with a command, not with a colour. A green check is a statement about the past tense of a machine I can't see. One rev-parse is a statement about now.

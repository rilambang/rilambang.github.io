AI-native development is a process, not a feature

4 min read · Muhammad Ilham Rilambang

"AI-native" describes how an app gets built. Nothing about it ships inside the app. The engineering that matters isn't the model either — it's the document you write so a tool with an empty context window can work inside a codebase that took years to shape.

I've spent the last weeks setting this up on my own projects — an agent harness in the editor, skills, plugins — and the installation is the easy half. These are the rules that survived contact.

An agent starts every task with nothing, so the document is the memory

The first surprise is how much of a good brief turns out to be a restatement of rules that were never written down. Which language mode. Which deployment floor. Which layer may call which. What "done" means. When to stop and ask rather than try harder.

Those conventions used to live in a senior engineer's head and in the review comments of a dozen pull requests. A tool with an empty context window can read neither. Written down once, they become the thing every task is briefed from — which is why that file matters more than the prompt, and why "I run an agent in my editor" describes almost none of the work.

What the IDE now gives you, and what it doesn't

This stopped being a bolt-on. The Xcode 26 release notes describe "coding intelligence features that help you write code, generate tests and documentation, fix errors, refactor existing implementations, and navigate codebases" — with a model of your choosing, including one that runs locally on Apple silicon.

Xcode 27 pushes further in exactly the direction this post is about: "Planning with agents is now first class in Xcode. Plans appear as editable Markdown artifacts next to the conversation" — review, annotate, discuss, and approve, before the agent proceeds. And the Xcode MCP server's tools now reach real platform state: manipulating the active run state, reading the debugger console, listing and switching schemes and run destinations, and inspecting or modifying build settings, compiler flags, entitlements and Info.plist keys.

That list deserves reading twice, because two of its items are the whole discipline in miniature. A plan you must approve before work starts is a review gate placed at the cheapest possible moment. Entitlements and Info.plist behind a tool call means the blast radius of a careless instruction now includes your signing configuration.

What the platform still doesn't ship is the part specific to your codebase. The harness is general; the conventions aren't. That asymmetry is where a person's leverage sits.

Four things I write down before the first task

  • Conventions — what the compiler and the linter enforce and, more usefully, what they can't: which layer may depend on which, where a string comes from, what an error is allowed to say.
  • Boundaries — the files an agent may touch, and the ones it must stop at and ask about. Credentials, permissions, payments, privacy surfaces and anything that leaves the machine are on the second list, always.
  • Definition of done — the exact command that proves the change. Not "looks right": a build, or a test that was red and is now green.
  • Stop conditions — after a few failed attempts, re-plan rather than try harder; never delete or skip a test to reach green; never widen the scope of a change without saying so.

The shape, as a pattern rather than anyone's real file:

Conventions        language mode · deployment floor · layer rules · where strings live
Boundaries         may touch: <paths> · must ask: credentials, permissions, payments
Definition of done the one command that proves it
Stop conditions    three failed attempts → re-plan · never skip a test · never widen scope
Roles              who plans, who writes, who verifies, who is allowed to fix

Two rules about what never goes into a prompt

Secrets and paths. A key prefix or a home-directory path isn't prose, so a word-by-word blocklist can never anticipate it — the check has to be shaped, not spelled. This site's own content check now fails the build on a key-shaped string or a /Users/<name>/ path in the published output. Not because a blog post would contain one, but because that class is guessable, and a script can hold a guessable class.

Transcripts. A real transcript is a document about your job; a pattern is a document about your craft. So I show the structure of a brief — the invariant, the constraint, the evidence — and never the text. The text carries whatever the session happened to contain, and nobody can write the blocklist for a conversation in advance. This is the rule I broke most often before I wrote it down.

What stays a person's job

Specificity. App Review is blunt about it: guideline 2.3.1(a) requires new features to be "described with specificity in the Notes for Review section of App Store Connect (generic descriptions will be rejected)". A generic description is exactly what a templated draft produces well — plausible, complete-looking, and about nothing. The model can draft; the specificity has to be mine.

The irreversible. Deployments, credentials, purchases, anything a revert can't undo.

The shape of the whole. Whether the feature should exist, where the seam belongs, which of two working designs will still be right in a year. An empty context window doesn't make any of that easier to delegate.

The pattern that keeps repeating: agents are good at the parts of engineering that are typing, and bad at the parts that are deciding. Most of the value of setting this up is the writing down — being forced to say, in plain language, which is which.

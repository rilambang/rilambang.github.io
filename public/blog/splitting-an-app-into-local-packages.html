Modularisation

Splitting an app into local Swift packages: what breaks first

4 min read · Muhammad Ilham Rilambang

Moving files into packages takes a day. Getting the boundaries right takes a quarter. The gap between those two numbers is where most modularisation projects quietly stall.

I've done this on more than one app now, and the failures are consistent enough to predict. This is the order things actually break in.

1. Resources, and the fact that they fail at runtime

The first casualty is anything that reads from the bundle. A JSON fixture, a font, a string file, an asset catalog image. Inside a package, the code needs Bundle.module. Code that still reaches for Bundle.main compiles perfectly and returns nil at runtime.

This is the worst class of breakage in the whole migration: it's invisible to the compiler, invisible in code review, and usually caught by a user rather than a test. Sweep for Bundle.main and UIImage(named:) before moving anything, and decide per call site whether it belongs to the package or to the app.

2. internal becomes public, and everything gets worse

The moment code lives in another module, internal stops being enough. The tempting response is to add public until it compiles. That is how a codebase ends up with a package that exposes forty types and enforces nothing — the boundary exists physically and not at all conceptually.

The test I use: if a package needs more than a handful of public symbols, it is not a module. It is a folder that happens to have a manifest.

So the real work isn't moving code, it's designing the API you wish existed and then making the code fit behind it. Write the interface first. If it's awkward to write, the boundary is in the wrong place, and you have found that out before the expensive part.

3. Build settings stop being inherited

A package doesn't inherit your app target's build settings. The Swift language version, the warnings you had silenced, optimisation flags, the deployment target — it's all declared in the manifest and is now a decision someone has to make deliberately. Do it in one pass, or you will spend a fortnight on warnings that appear in one module and not the adjacent one.

4. Names collide immediately

Every modular codebase has a User, a Config, an Extensions, a Logger. Once they're in separate modules they're all legal and all ambiguous at every call site. Type names have to say what they are now — which sounds like a nit and is actually a boundary leaking into every file that touches two modules.

5. Tests can't see across the wall either

@testable import works for a package's own tests. It doesn't let a test in one module reach into another's internals. That is the point, but it means tests that were quietly testing implementation details have to be rewritten against the public surface — or the surface has to grow to make the behaviour testable. The second option is usually correct, and it's a useful signal that something is missing from the API.

6. The awkward middle, and why people quit here

For a while, everything is public, nothing is faster, and there are more files than before. That isn't the design failing; it's the design being incomplete. The end state — narrow public surfaces, small rebuilds, obvious ownership — is what pays. Judge it at the end, not in week two.

7. Cycles surface, which is the whole point

The first genuinely valuable thing modularisation does is make circular dependencies compile errors. In a single target, A using B and B using A is invisible. Across module boundaries it can't exist.

That error isn't an obstacle in your way. It is the design bug you had been hiding, finally unable to hide. The wrong fix is to merge the two modules so it compiles again.

The sequencing I'd use again

  1. Leaves first. The things that depend on nothing: design tokens, models, a networking core, a logger. Low risk, immediate proof that the tooling works.
  2. Then the middle. Shared UI, shared services. This is where the API design conversation actually happens.
  3. Feature modules last. They are the ones that need the seams below them to be settled, and the ones most likely to move again if they aren't.
  4. The app target ends up a shell. Composition, navigation, configuration. If the app target still contains business logic, the split isn't finished.

The thing I would do differently: agree the vocabulary and the public surface before anyone starts moving code, in writing, and treat a change to either as a design decision rather than a refactor. Moving files is mechanical. Everything that made the project worth doing isn't.

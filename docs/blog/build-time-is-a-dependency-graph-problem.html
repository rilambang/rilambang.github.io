Build systems

Build time is a dependency-graph problem, not a machine problem

When builds get slow, the first proposal is always a better machine. A faster Mac buys a constant factor. The dependency graph is the exponent.

Apple's own guidance on incremental build performance is worth reading before optimising anything, and it is refreshingly blunt: the things that break incrementality are the things that make the build redo work it did not need to redo. That is a graph problem.

Measure the build, not the vibe

Before changing a setting, get the timing summary from a build and look at where the time actually goes. Two facts usually fall out immediately:

  • One or two tasks dominate, and they are not the compiler.
  • The build is compiling far more than the change touched.

Both point at structure rather than at hardware.

The most common culprit is a Run Script phase

A script phase with no declared inputs and outputs runs on every build. It does not matter that the script is quick. The cost is not the script's runtime, it is that it invalidates downstream work and forces the build to redo it. A five-line script can be responsible for minutes.

Three responses, in order of preference:

  1. Delete it. A surprising share of script phases exist to do something the build system already does, or to copy a file that should be a build setting.
  2. Declare inputs and outputs. If the script genuinely generates something, tell the build system what it reads and what it writes, so it can be skipped when neither changed.
  3. Move it somewhere it is not on the critical path — earlier in the pipeline, or out of the build entirely.

Then look at what a change actually invalidates

In a single-target app, the answer is usually "everything downstream", which is to say "most of the app". A change to a shared file in a large target can recompile a majority of the codebase — not because the compiler is slow, but because the unit of work is the target.

Splitting the target is the fix, and the reason it works is not micro-optimisation. It is that an unchanged module is genuinely unchanged, and the build system can skip it. The incremental case — which is the case you live in, hundreds of times a day — gets faster by an order of magnitude rather than by a percentage.

Whole-module optimisation, and the debug/release asymmetry

Whole-module compilation is faster for a clean build and much worse for an incremental one, because the module is the unit that must be redone. The interesting consequence is that your debug builds and your release builds want opposite things, and a configuration that is right for one is wrong for the other. Decide per configuration rather than applying one global preference.

Type-checking hot spots are real and they are local

A single expression that the type checker cannot resolve quickly — a large literal, a deep nesting of operators, a long chain of overloaded calls — can take longer to compile than the file around it. The compiler will tell you if you ask it, and the fix is to make the expression simpler or to name the type explicitly. It is a small, contained edit with an outsize effect.

Asset catalogs

Assets are compiled, and a large catalog that changes often is a step you pay for repeatedly. Keeping generated or throwaway assets out of the catalog is not a style preference; it is build time.

What I'd tell a team staring at a slow build

  1. Get the timing summary. Guess nothing.
  2. Delete or declare script phases. Cheapest win available, almost always.
  3. Split the target so unchanged code can be skipped.
  4. Fix the one or two type-checking hot spots the compiler names.
  5. Only then consider hardware or caching, and expect a constant factor rather than a step change.

The uncomfortable part is that the first four are all structural. The build is slow because the code is shaped in a way that makes it slow, and no amount of machine fixes a shape.

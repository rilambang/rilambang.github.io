How I review iOS pull requests

3 min read · Muhammad Ilham Rilambang

A review that starts with naming has already wasted its most useful attention. Here is the order I read a diff in, and the things I refuse to merge.

The order

  1. Does it do what the description says? Not what the code says — what the description claims. If they diverge, that is the first comment, before anything else.
  2. Can it crash? Force unwraps, array indexing, casts, anything that assumes a shape it has not checked.
  3. What is the failure path? Every network call fails. Every write can be interrupted. A diff that only handles success is half a diff.
  4. What was deleted? Removed guards and removed tests first.
  5. Style. Last, and usually not at all.

Three questions, every time

  • What happens on a slow network? Not down — slow. That is the state where double submissions, spinners that never resolve, and buttons that fire twice live.
  • What happens if the user backgrounds the app mid-operation? Very few diffs survive this question unconcerned, and the ones that do are the ones I trust.
  • What happens the second time? Is this operation idempotent? Retrying a payment, a submission, a sync — the second call is where data loss is born.

What I refuse to merge

  • A skipped or disabled test. If it cannot pass, delete it and say so; a disabled test is a lie that gets inherited.
  • A test that asserts nothing, or that asserts the mock.
  • try? on a write. Swallowing a failed save is how a user loses an hour of work and nobody finds out.
  • A new dependency for something the platform already does.
  • A control with no accessibility label. This is not a later ticket; it is an unfinished control.

Concurrency, because that is where the crashes actually are

Most of the real defects I find in review are structural rather than logical:

  • A task started from a view that outlives the view, and writes to state after it is gone.
  • State mutated off the main actor that a view reads on it.
  • Two writes racing to the same store with no single owner.

These do not need a deep read of the logic. They need one question: who owns this state, and on which actor is it touched? If the diff cannot answer in one sentence, that is the comment.

Two habits that pay

I review the smallest possible unit, early. A large diff gets a shallow read and a rubber stamp, and both parties know it. Several small diffs get real attention. If a change is too big to review carefully, the review is not the problem to fix — the change is.

I explain the failure, not the rule. "This will double-submit if the user taps twice before the response" teaches something. "Don't allow double taps" produces a fix for this instance and the same bug next month. The comment that names the failure mode is worth ten that quote the standard — and it is the difference between a review and a gate.

What review is for

Not catching typos, and not demonstrating that the reviewer read the code. It is the last point at which the person who wrote something still remembers why, and someone else can ask "what happens when this goes wrong?" while the answer is cheap. Everything else about it is negotiable. That is not.

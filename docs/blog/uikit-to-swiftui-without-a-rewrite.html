Migration

UIKit to SwiftUI without a rewrite

3 min read · Muhammad Ilham Rilambang

The migration succeeds or fails on one decision: who owns navigation. Get that right and the rest is a sequence of small, reversible steps. Get it wrong and you end up with two systems that each half-know where you are.

I've taken more than one shipped app across this boundary. Nobody regrets the destination. People regret the order.

Don't start with the app shell

The instinct is to rewrite the root and let the screens follow. That inverts the risk: the shell is the part every screen depends on, and it's the part you can't ship incrementally.

Start with leaf screens — a detail view, a settings page, a form. Screens that don't own navigation are the safe unit of migration, because failure costs you one screen rather than the app.

Pick one direction of interop at a time

The two directions aren't symmetric and should not be started together:

  • UIKit shell, SwiftUI leaves — a UIKit view controller hosts a SwiftUI view. This is the low-risk direction, and it's where a migration should begin.
  • SwiftUI shell, UIKit leaves — a SwiftUI view wraps a UIKit component. Necessary for the handful of things SwiftUI still doesn't do well, and the direction that tends to accumulate if you're careless.

Whichever you're in, know which one it is. A codebase that's doing both, everywhere, with no rule, has no migration at all.

Navigation is the seam, so give it exactly one owner

This is the decision that determines whether the migration is a project or a permanent tax. Two systems that both believe they own the stack produce bugs that are extremely hard to diagnose: a screen that appears twice, a back button that does nothing, state that resets on pop.

Keep navigation in one place for the whole migration — whether that's the UIKit navigation controller or a SwiftUI stack driven by a coordinator. The other side renders content and reports events. It doesn't push.

State ownership: pass data in, events out

Don't let the two worlds observe each other's state. A view controller watching a SwiftUI observable object, or a SwiftUI view holding a reference to a view controller and polling it, is a future bug in both directions.

The contract that survives: the parent passes a value in and receives callbacks out. That is enough for almost every screen, and it keeps either side replaceable.

What actually bites

  • Keyboard avoidance. Two systems, two opinions, one screen. This is the most common source of visual regressions during the swap and it's worth a dedicated pass.
  • List identity. A list that reuses cells and a list that keys on identity behave differently on update. Missing or unstable identity produces animations and state loss that look like a rendering bug and aren't.
  • Lifecycle timing. "Appeared" doesn't mean the same instant in both systems. Code that kicks off work on appear and cancels on disappear will behave differently, and the difference shows up under a slow network, not on your desk.
  • Measurement. Geometry readers used for layout maths are a smell in a declarative system. Most of the time the layout you were computing by hand is a two-line native layout, and the manual version is the expensive one.

Availability is part of the plan, not an afterthought

Everything you adopt has to exist on your deployment target, and anything newer needs a working fallback — not an #available that silently renders nothing. Write down the minimum supported version and treat every adoption above it as a decision with a cost.

How you know it's finished

The app target compiles without importing the old UI framework outside the places the platform genuinely requires it. Until then, you have a mixed app, which is a perfectly good state to ship from — but it's a state, not an outcome. Name the finish line, or the migration becomes the architecture.

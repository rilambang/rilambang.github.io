A design system is a review policy, not a library

2 min read · Muhammad Ilham Rilambang

A design system is not a package you import. It is a set of decisions that review enforces, and the package is only the place those decisions live.

I have watched more than one design system die at screen three. The failure is always the same and never looks like a design problem at the time: someone had a deadline, the component almost fit, and they wrote the value inline. That file is now the precedent.

Three copies of every value

In a healthy system there are exactly two places a colour can come from: the design source, and the token that mirrors it. In a real codebase there is a third — the literal somebody pasted into a view — and that is the one that ages badly. It does not break. It just drifts, one hex at a time, until nobody can change the brand colour without a treasure hunt.

What makes it stick

  1. Token names describe intent, not value. surface, danger, border-subtle survive a redesign. grey300 does not, and it invites the next person to pick a neighbouring number by eye.
  2. The default has to be the correct one. If using the system is harder than not using it, the system loses, every time, to someone under pressure. Convenience beats policy.
  3. The component owns its own spacing. A system where every screen re-specifies the padding of the same button is a component in name only.
  4. Review rejects the override. This is the actual enforcement. Not a lint rule, not a guideline — a person saying no, in a review, with a reason. The first few of those set the norm for the next hundred.

What I check in review

  • No raw colour values outside the tokens file. None, including "just for the shadow".
  • No font sizes written as numbers in a view.
  • Spacing from the scale — not 13 because it looked right that afternoon.
  • A component not re-specifying spacing the component already defines.
  • New tokens: does an existing one already mean this? Duplicated intent is how a token file becomes a colour palette.

The honest cost, said out loud

A design system slows down the first screen and speeds up the tenth. That is the entire trade, and it is a bad deal if you only ever build one screen. Teams abandon systems because nobody said the first half of that sentence, so the first screen feels like overhead and the tenth never arrives.

Say it in the same breath as the plan. "This will be slower for a fortnight and faster after that" is a sentence a team can agree to. "We are adopting a design system" is not.

The design side is a person, not a handoff

The systems I have seen work have a designer who reads the diff, or a developer who has the design file open. The ones that fail have a Figma link and a prayer. The gap between the mock and the implementation is where defaults get invented — and invented defaults are the beginning of the third copy.

None of this is about tooling. It is about which choice is the path of least resistance on a Thursday afternoon, and who is standing between the deadline and the hardcoded hex.

MVVM to Clean to VIPER: three architectures, one exam app

7 min read · Muhammad Ilham Rilambang

The review comment that started this was one I wrote on my own diff: why does the exam view model know the network layer, the router, the answer queue, and the invigilator? Three architectures later, the answer is that nothing in MVVM said it couldn't — and every migration since has been about getting the compiler to say no.

The app is a proctored exam client: a million students sit exams on it, usually on school Wi-Fi, usually with someone watching them. That prices every architecture decision differently. A failed exam is not a bad afternoon, and the modules have to keep shipping while the structure moves underneath them.

Act one: MVVM, when the view model is the app

MVVM is the right answer at the size where most of us meet it. A screen, some published state, a service in the initializer. You can hold the whole feature in your head.

Then the feature grows, and nothing in MVVM stops growth from landing in one place. The exam screen's view model ended up owning:

  • what state each question is in — answered, flagged as unsure, untouched;
  • the rule for when an answer is allowed to leave the device;
  • the offline answer queue and its retry pump;
  • navigation through the exam gate;
  • and the HTTP calls, because importing the network manager was one line and a review away.

MVVM has no opinion about where business rules live, so they live in the view model. No opinion about navigation, so navigation lives in the view model. No opinion about data shapes, so the view model starts speaking in wire types. Ours took the API's finish payload straight at the seam where the screen said "finish". That is the tell: the UI is now authored by the backend schema.

Testing followed the same shape. To test one rule you built a view model, mocked a network manager, subscribed to a Combine sink, and hoped. Fourteen exam suites lived in the app test target, so a rule about the answer queue could not be tested without building the app.

None of that was a skill problem. It was a blast-radius problem: every rule had access to everything, so every change could touch anything.

Act two: clean, or make the compiler hold the line

The first correction was not a rewrite of the view model. It was a wall.

Per feature: a domain target with entities and repository protocols, a data target with the real repository, mappers and the network, and a feature target with the view and its state — separate local packages with an acyclic graph between them. The folder names are not the point. The point is that the graph is a compiler fact: a presenter that imports the networking module does not get a review comment, it gets a build error.

That one property paid immediately:

  • Rules became testable in milliseconds. No UIKit, no network, no app. An interactor and a fake repository.
  • Wire types stopped leaking. A mapper moves wire type to entity and back, with round-trip tests, so the day the backend renames a field the diff is one file instead of eleven screens.
  • Reuse stopped meaning "copy". Question types moved behind their own models instead of being open-coded per screen.

And then it over-delivered, the way architecture tends to.

The bill for clean: forty-three packages

Three layers per feature, times eight features, plus a dozen shared core modules, and we were at 43 sibling packages. Each one: its own repository, its own manifest, its own row in the lock file, its own entry in the CI path list, its own checkout to keep in sync. A single feature crossed three repos. A cross-cutting change was a three-repo merge request with a lock bump.

Layering made the code cleaner and the work heavier. Clean boundaries are cheap per module and expensive per module count, which is the trade I had not priced in. At 43, the module system had become a second product we maintained.

There was a quieter failure too. Clean gave us a home for entities and repositories, but the view model still had three jobs: view state, use-case orchestration, navigation. The data layer got better and the screen did not change at all.

Act three: VIPER, which is mostly a rename and a confession

Here is the part that does not go in the architecture diagram: we did not adopt VIPER because it is better on paper. We adopted it because the view model had already become a presenter, and naming it one was the cheapest way to stop the next person from putting rules back into it.

The migration was mostly mechanical, which is the best thing you can say about an architecture change on a product a million people depend on:

  • Twenty-two view models became presenters. Type names are documentation that survives a rewrite. Nobody reads the architecture doc; everyone reads autocomplete.
  • The rules moved out, one use case at a time — load the questions, submit an answer, poll the status, report an isolation event, finish, flush the offline queue. Each owns one rule, and each is testable with a fake.
  • The router got a real job. Feature routers own "where does this button go"; the app-level coordinator still owns the stack. A VIPER router is often a god object, and a single owner above it is what prevents that.
  • The last wire type left the domain. The network layer can now change without touching a screen.
  • The question views came home. They had been in the shared UI package, which meant every feature that wanted a checkbox imported the exam module's world. The core lost three dependencies.
  • The tests came home too. Fourteen suites moved into the feature package, which let us delete five test-only escape hatches that existed so app-side tests could reach presenter internals. Deleting an escape hatch is better architecture than adding a protocol.

The module count went from 43 to 19: one package per feature, exporting the same three products under unchanged names, so not one import line changed. That is the only reason a 43-to-19 consolidation landed as a series of boring commits.

The layout is now the thing you can explain in ten seconds: entity and interactor in the domain, repository and mappers in data, view, presenter and router in the feature.

What actually made the migration possible

Not the architecture. The operations around it.

A pilot and a script. One feature was consolidated by hand, a merge script was written from the exact commands that worked, and the remaining slices ran through it. Mechanical batches do not get eight review loops; they get one reviewed script.

A lock file and a sync step. A revision pinned per module, and a sync that fails loudly on drift. Without that, nineteen packages times eight engineers is a support desk.

A gate that could say no. Device build, the full app suite, every package suite, lint. Once at the end of a batch, not per slice. And for the exam slice specifically, a real proctored exam on a real device: start, answer offline, restore the network, flush, finish, isolation path. A simulator pass does not prove a queue replays.

A build-only rule for the mechanical work. During the rename and the consolidation the compiler was the gate, and the full suite ran once at the end. That sounds reckless. It was not: the changes were renames and file moves, and running a thousand tests after each of twenty-two renames turns a two-day job into two weeks. The rule had a written expiry date, and the full gate ran before anything shipped.

What I would do differently

  • Price the ceremony, not only the boundary. One package per feature with three targets inside would have given the same compiler walls with a third of the bookkeeping.
  • Do not clean the layer that is not hurting. I improved data access for months while the screen kept growing. The screen was the problem.
  • Migrate the riskiest path first. The exam is the app, and we did it last. Doing it first would have been scarier, and it would have found the real constraints before three other slices depended on them.
  • Give navigation a deliberate owner on day one. Every architecture lets the router drift into everything or nothing. "The coordinator owns the stack, feature routers own the destination" is a five-minute decision that saves a rewrite.

The honest summary

MVVM got the app to a million students. Clean made the data layer testable and the boundaries real, and cost us a module system. VIPER fixed nothing Clean had not already fixed — it made the last unowned thing, the screen, own its responsibilities, and made the architecture readable in autocomplete.

If you are choosing today: MVVM while the feature fits in one head, clean boundaries the moment a rule has to be tested without a screen, and VIPER when navigation is a product rule rather than a detail. Here navigation is the product — a gate, a consent screen, an invigilator watching — so VIPER earned its ceremony. Most apps do not have that, and should not pay for it.

The architecture that wins is not the one with the most layers. It is the one where the compiler can tell the next engineer no without me in the room.
